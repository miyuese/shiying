## 阅读指引 · 术语对照

插件分「前台」（你看到的界面）和「后台」（看不见的、真正调 AI 干活的 Service Worker）两部分。
前台和后台之间通过「发消息」通信，图片以两种形态传递：

| 术语 | 大白话 | 说明 |
|---|---|---|
| dataURL | 照片的电子副本 | 完整图片内容（Base64 字符串），体积大 |
| blobKey | 取货单 / 存单号 | 图先存进 IndexedDB，只传一个编号过去，体积小 |

**核心结论先看这段**：后台的生成流程「只认取货单，不认照片副本」，而前台所有按钮发的都是「照片副本」——于是图在路上丢了。同时后台要用「压缩工具」，可压缩工具只存在于前台，后台一用就报错。这两条是全部问题的根源，其他都是分支。

## 一、致命 · 核心链路断裂（功能整体不可用）

### P1. 所有「带参考图生成」的功能，参考图在后台被静默丢弃

**用户症状**：
- 换脸 → 生成结果的脸跟人物卡完全不像，等于随机文生图；
- 拍一套 → 生成的四宫格跟参考人物无关；
- 重绘 → 构图和参考图毫无关系；
- 人物卡「重新生成」→ 生成的三视图不带原图人物。
- 且任务状态显示「已完成」，无任何报错，极具迷惑性。

**位置**：
- 后台执行器：`src/background/router.ts:354-355` —— `runGenerate` 只读 `p.sourceBlobKey` / `p.faceBlobKey`（取货单），**从不读** `p.sourceRef` / `p.faceRef`（照片副本）。
- 前台各视图发的却是照片副本：
  - 反推重绘 `src/panel/views/analyze.ts:132-137`（`sourceRef: state.selectedImage`，`faceRef`）
  - 换脸 `src/panel/views/faceswap.ts:70-76`
  - 拍一套 `src/panel/views/suite.ts:63-69`
  - 人物卡重生成 `src/panel/views/personCard.ts:147-153`（`sourceRef: dataUrl`）

**根因**：`GeneratePayload` 类型（`src/shared/types.ts:150-164`）注释声明 `sourceRef/faceRef` 与 `sourceBlobKey/faceBlobKey`「二选一」，实现却只实现了 blobKey 一条通道。前后台各用一半，接不上。

**唯一正常路径**：新建人物卡 `src/background/router.ts:121-145` —— 它先把图存 IndexedDB，再传 `sourceBlobKey`，所以人物卡三视图能正常生成。可作为「正确写法」参照。

**修复方向**：在 `runGenerate` 里补充「若收到 `sourceRef/faceRef` dataURL，则先 `toBlob` 存 IndexedDB 再取回」，或前台改为统一走 blobKey 通道。二选一，两端对齐即可。

### P2. 图片输入依赖 DOM 压缩，在后台必然报错 → 网页取图 / 上传 / 网页收集全失败

**用户症状**：
- 网页上悬停图片 → 点蓝色「影」按钮 → 面板打开了，但图没进来；
- 面板「网页收集」→ 弹「无法读取网页图片」；
- 面板「上传」→ 弹读取失败。
- 全项目**只有「相册」选图能用**，等于「图不进相册就进不了插件」。

**位置**：
- `src/shared/utils/image.ts:41-61` `compressImage`：内部 `loadImage` → `new Image()`，再 `document.createElement('canvas')` + `ctx.drawImage` + `canvas.toDataURL`。
  - `new Image()` / `document` / canvas **只存在于浏览器页面环境**，Service Worker 里没有 → 一调用就抛 ReferenceError。
- 后台三个消息处理器都调用了它（后台 = Service Worker）：
  - `image-from-url` `src/background/router.ts:204`（网页悬停图、popup 快捷图、面板网页收集都走它）
  - `image-from-album` `src/background/router.ts:212`（未被任何调用方使用，属死代码）
  - `image-upload` `src/background/router.ts:217`（面板上传）

**受影响链路**：
- 网页「影」按钮：`src/content/index.ts:245-264` —— `image-from-url` 抛错被 `catch {}` 吞掉 → 面板开、图没进来；
- popup 快捷操作：`src/popup/index.ts:131-141` `storePendingImage` 同样失败被吞 → 面板无图；
- 面板网页收集 / 上传：`src/panel/components/imageSelector.ts:56-59`、`:89`。

**根因**：把「浏览器页面环境才有的 API」在 Service Worker 里使用，属于环境误用。且调用方大多用 `catch {}` 静默吞错，用户只见「没反应 / 图没进来」，看不到真实原因。

**修复方向**（三选一）：
1. 把压缩逻辑改成纯数据层实现（如用 `createImageBitmap` + `OffscreenCanvas`，SW 可用）；
2. 或压缩放到前台（panel）做，后台只收成品 dataURL；
3. 或干脆去掉压缩，直接存原图。
另：`image-from-album` 若保留，需同样处理。

### P3.（连带 P2）拼图法 fallback 也在后台用 canvas，双图不支持时照样炸

**用户症状**：换脸/重绘带双图（源图+人脸）时，若服务商不支持多图上传，插件本应自动降级成「拼图法」，但降级路径也会静默失败 → 生成报错。

**位置**：
- `src/background/providers/generate.ts:118-145` `retryWithComposedImage`（在后台运行）→ 调用 `composeFaceBadge`
- `src/shared/utils/image.ts:96-125` `composeFaceBadge`：同样是 `new Image()` + canvas 实现 → SW 里 ReferenceError。

**根因**：与 P2 同源，canvas 依赖。

## 二、高 · 功能存在但被卡死

### P4. 「不选人脸（纯反推）」按钮是死按钮，且自动选卡导致无法清除

**用户症状**：想「纯反推、不带人脸」生成，永远做不到。界面有按钮、有说明，点了没反应。

**位置**：
- `src/panel/views/analyze.ts:43` 渲染了 `#btn-skip-face`，但全文**未绑定任何 click 事件**；
- `src/panel/index.ts:83-88` `refreshPersonCards` 在 `selectedCardId` 为空时自动选中默认卡/第一张卡，用户无「清空选择」入口 → 永远有卡被选中。

**修复方向**：给 `#btn-skip-face` 绑定事件（清空 `selectedCardId`）；或提供「不使用人脸」的显式选项。

---

### P5. 默认生图模型名非法，开箱即 404

**用户症状**：新用户填好 API Key 直接生成 → AI 返回「模型不存在」，生成永远失败，误以为插件坏了。

**位置**：
- `src/shared/constants.ts:56` `DEFAULT_SETTINGS.generateApi.model = 'gpt-image'`（真实可用为 `gpt-image-1`，少了个 `-1`）；
- `src/shared/constants.ts:75` `GENERATE_MODEL_OPTIONS = ['gpt-image', 'gpt-image 系列']` —— 均非公开可用的模型名（gpt-image 系列 是内部代号）。

**修复方向**：改为真实模型名；模型选项建议做成「可自定义输入 + 常用列表」，而非写死两个选项。另注意 `docs/拾影-ShiYing-PRD.html` 及设置页引导文案中若提到这两个名字也需同步。

## 三、中 · 明显不可用

### P6. 「取消任务」是空操作

**用户症状**：点取消 → 界面显示「已取消」，但任务照跑，跑完还会被改回「完成」。

**位置**：
- `src/background/tasks.ts:127-129` `cancelTask` 只把状态改成 `cancelled`；
- 注释声称「由调用方中断 AbortController」，但 `enqueue`（`tasks.ts:190-200`）、`runGenerate`（`router.ts:348-415`）、provider 全程**没有任何 AbortController / 中断信号**，HTTP 请求照发，回包后状态被覆盖回 done/failed。

**修复方向**：要么真正实现 AbortController 并在 `runGenerate`/provider 透传；要么接受「取消后仍可能完成」，并在 UI 上说明。

---

### P7. 网页「影」按钮永远打开浮动窗口，侧边栏永远打不开

**用户症状**：点「影」总是弹出一个 420×720 的小窗口，而不是 Chrome 右侧侧边栏。

**位置**：
- `src/background/router.ts:269-284` `open-panel`：`chrome.sidePanel.open` 要求用户手势，经 background 转发后手势丢失 → 必然走 catch 兜底成 `chrome.windows.create` popup 窗口。
- 对比：popup 自己有手势、能正常开侧边栏（`src/popup/index.ts:110-122` 直接在 popup 内调用 `chrome.sidePanel.open`）。

**修复方向**：content script 里的「影」按钮要么先打开 popup 再让 popup 去开侧边栏（借 popup 的手势），要么用 `open-panel-fallback` 明确告知用户是独立窗口。

## 四、低 · 次要缺陷 / 假功能

### P8. 结果区「再生成」是纯占位按钮

- `src/panel/components/resultBar.ts:77-78`：点击只 toast「重新生成本地已存图（演示）」，无实际功能。

### P9. 结果区状态文案恒为「完成」

- `src/panel/components/resultBar.ts:12` 先 `filter(t.status === 'done')` 再渲染 → 第 24 行的 `failed / running` 分支是死代码；失败/进行中的任务根本不会出现在结果区。

### P10. popup 每次打开都重复注入一份 content script

- `src/popup/index.ts:27` 每次 init 都发 `inject-content`；
- `src/background/router.ts:298-314` `executeScript` 不做去重 → 同一页面会叠加多个悬浮层实例、重复监听，浮层可能重复出现。

### P11. content script 监听器在「扩展页守卫」之前注册

- `src/content/index.ts:311-319`：`addEventListener`（pointermove/scroll/resize）先注册，`location.protocol === 'chrome-extension:'` 判断在第 319 行才 return → 扩展页里监听器已挂上（浮层虽不显示），`shiyin-get-last-image` 监听（323 行）也始终生效。
- 建议把守卫提到 `init()` 最前面。

### P12. 反推时大图原样直传，无压缩

- `src/background/router.ts:163-165` `analyze-image` 把 `imageDataUrl` 直接交给 provider（`src/background/providers/analyze.ts`）→ 超大图可能超出视觉 API 体积限制。

### P13. 人物卡「等待生成」超时检查匹配到的是别人的任务

- `src/panel/views/personCard.ts:41-53`：用 `tasks.find(t => t.type === 'personCard' && running)` 匹配**任意**一张卡的任务，而非当前这张卡自己的 → 多卡并发时可能误判/漏判，把别人的超时算到这张卡头上。

### P14. 测试连接用 256×256 测生图，且误报「端点可达」

- `src/background/providers/test.ts`：主端点 404 时降级 `images/generations` + `size: 256x256`，而 `gpt-image-1` 不支持该尺寸；非 401/429 一律算「端点可达」→ 测试结果有误导性，配置了不支持的模型也会报通过。

### P15. 四宫格切分图按 1:1 展示，与所选画幅不符

- `src/panel/views/suite.ts:158` 切分后的单格固定 `aspect-ratio:1/1`；若生成画幅是 3:4 / 9:16，单格实际是 3:4 / 9:16，会被拉伸显示。需按 `task.inputs.aspectRatio` 动态设置。

### P16. 纯反推模式（未选人物卡）提示词仍包含"人脸参考图"说明（2026-08-12 补充）

**用户影响**：重绘页不选人物卡时只发一张构图参考图，但 `REDRAW_GUIDE` 仍整体拼入 prompt，其中"人脸参考图（= 人物卡）作为人物面部身份的来源"一段会让模型以为存在第二张人脸参考图——理论上可能让模型脑补/虚构一张人脸，导致生成画面出现"凭空多出来的人脸"。

**位置**：
- `src/panel/views/analyze.ts:126-138` —— `faceRef` 仅在有选中人物卡时才赋值，否则为空；
- `src/background/providers/generate.ts:74` —— 仅 `hasSource && hasFace` 才加"双图分工"前言（单图时不加，这是对的）；
- `src/shared/prompts.ts:101-103` `buildRedrawPrompt` —— **无条件**拼入完整 `REDRAW_GUIDE`，未按是否带人脸参考裁剪。

**修复方向**：按是否有 `faceRef/faceBlob` 裁剪——无人物卡时用去掉"人脸参考图"段的精简版（只保留"构图参考图"说明）；有卡时用完整版。可给 `buildGeneratePrompt` 传入 `hasFace` 参数，或在 generate.ts 组装处裁剪。

## 六、两条根源（修复优先级建议）

1. **参考图通道前后台不一致**（P1）——前台传 dataURL，后台只认 blobKey。决定一条标准通道（建议：后台统一收 dataURL → `toBlob` 入 IndexedDB → 之后全用 blobKey），把两端对齐。
2. **后台误用页面环境 API**（P2/P3）——canvas / `new Image()` 只能在页面环境用。把压缩/拼图逻辑改为 SW 可用实现，或移到前台执行。

先修 P1、P2/P3，P4、P5 次之，其余按体验优先级逐个处理。
